# Recommended session-level partition (splits.csv)

`splits.csv` assigns each of the 23 sessions of deposit v1.2 to one of `train`, `validation` or `test`. The assignment is a recommendation for machine-learning use of the corpus; nothing in the deposit depends on it. It is regenerated by [`pyscripts/build_dataset_card.py`](https://github.com/mormegil6/hoa-corpus-ieee-access/blob/main/pyscripts/build_dataset_card.py) in the analysis repository at <https://github.com/mormegil6/hoa-corpus-ieee-access> (the assignment itself is the `PARTITIONS` constant in that script).

## Columns

| column | meaning |
|---|---|
| `session_id` | session directory name under `sessions/` |
| `partition` | `train`, `validation` or `test` |
| `venue` | venue slug taken from the directory name |
| `content_type` | `content.type` from the session's `metadata.yaml` |
| `primary_mic` | `equipment.primary_mic_model` from `metadata.yaml` |
| `mics` | every array with a render in the session (from filenames) |
| `duration_min` | sum of all rendered B-format file durations in the session, minutes (from the file scan; parallel captures counted separately) |
| `programme_min` | `duration_minutes` from `metadata.yaml`: unique programme time, parallel captures counted once |
| `files` | number of rendered B-format WAV files in `audio/` |
| `a_format_files` | number of A-format WAV masters in `audio_a_format/` (2024-08-15 only) |

Shares and totals are computed from unrounded per-file durations; summing the one-decimal `duration_min` column of `splits.csv` gives 652.2, 136.8, 172.7 and 961.7 min.

Shares by file duration are 68/14/18 rather than 70/15/15 because the mandatory test session (2024-08-15) alone is 142.1 min of files (14.8 % of the corpus): it holds four parallel renders of the same programme (`programme_min` 35.8 from the session metadata; the two renders sum to 35.5 min). By unique programme time the test partition is 9.1 % of the corpus. Users who count parallel captures once should read the `programme_min` column.

### train (16 sessions)

Everything else: ten Aula sessions (solo piano, piano duet, choir, violin-piano duo, the 2024-04-30 ZM-1/Spcmic pair), both Gdańsk Tech lobby concerts, Holy Trinity church, Oliwa Cathedral (Spcmic only), the aMuz concert hall, and the Piechcin quarry VR production.

## The leakage rule

All files of a session are in the same partition, and no segment of one continuous recording may appear in two partitions. This is what keeps the partition leakage-safe, and anyone who re-cuts the corpus has to preserve it:

- Several "files" are segments of one continuous take. `2022-04-21` is a single 3OA take rendered into six files (`CharityConcert01`-`06`); `2022-03-10` and `2023-10-12` are one concert each in two parts (`Pt1`/`Pt2`); the Haydn sonata movements and the Bach preludes and fugues of `2022-04-13` are each files of one multi-movement work. Splitting these by file would put adjacent minutes of the same performance in different partitions.
- Parallel renders of one performance (ZM-1 + NT-SF1, ZM-1 + Spcmic, Spcmic 3OA + 5OA, and the eight renders plus six A-format files of 2024-08-15) are the same acoustic event through different arrays and encoders. They must never be separated, including the A-format masters. Note that the renders of one performance are not time-aligned with each other: in 2024-08-15 the Franck Spcmic render begins 7.77 s earlier in real time, so a given musical moment sits 7.77 s later in its file, and on the Prokofiev the offset runs the other way by 7.92 s, so any protocol pairing arrays frame by frame must align them first.
- Any windowing (for example the 5 s segments used for the neural renderer cited in the paper) must be done inside a partition, never on the pooled corpus.

The split is session-disjoint only. It is not performer-disjoint (Piotr Pawlak plays in train, validation and test; the Gdańsk Tech Academic Choir appears in train and validation; Mikołaj Sikała's four sessions are all in train), not instrument-disjoint (the Aula's Steinway D, serial D560633, is in all three partitions) and not venue-disjoint (Aula PG is in all three partitions). Models that would learn a performer, an instrument or a room rather than the target quantity should be evaluated with the restricted protocols below.

## What venue- and microphone-independent evaluation the corpus allows

The corpus is small and unbalanced (15/23 sessions on the Gdańsk Tech campus, one ZM-1 unit in 21/23 sessions), so independence can only be tested in limited forms:

**Unseen venue in test.** Both non-Aula test venues (Fiqu Miqu studio, Sopot pier) occur in no other session, so scores on those two sessions (30.6 min) are unseen-venue scores. The Aula part of the test set (2024-08-15) is not an unseen-venue score: 12 other Aula sessions are in train and validation.

**Leave-one-venue-out.** Every non-Aula venue except the Gdańsk Tech lobby is a single session (Holy Trinity 79.5 min, Gdańsk Tech lobby 2 sessions/154.1 min, Sopot 11.4, Baltic Philharmonic 74.4, Fiqu Miqu 19.2, Piechcin 3.2, aMuz 15.2, Jędrzejewo 4.5, Oliwa 100.0). A leave-one-venue-out protocol therefore has one session per fold and cannot estimate variance across sessions of the same room. Aula PG cannot be held out without discarding 13/23 sessions and 59/74 files.

**Unseen microphone.** The arrays that never occur as a session's only microphone are NT-SF1 and SR-VRMIC. Of the two, only SR-VRMIC is held out by the recommended partition, both its renders being in test; the eight NT-SF1 renders sit in train and validation. For either array, each of their renders has a same-session ZM-1 twin, so a "train on ZM-1, test on NT-SF1" protocol is possible only within the session pairs (2021-06-27, 2023-06-03, 2024-12-10, 2025-02-05 for NT-SF1; 2024-08-15 for SR-VRMIC) and always tests on the same programme the ZM-1 twin was recorded on. The Spcmic occurs alone in two sessions (2025-09-28 in validation, 2026-01-18 in train), so "train on ZM-1 sessions only, test on Spcmic-only sessions" is possible on 104.5 min but confounds microphone with venue (cave set, cathedral) and content.

**Paired-array transfer.** The two co-located ZM-1/Spcmic sessions are the only microphone-transfer path free of a venue or content confound: train an array-to-array mapping on the 2024-04-30 pair (train partition, 15.4 min of programme, same hall and piano, 17 cm apart on one bar) and evaluate on 2024-08-15 (test). Both are Aula solo piano, so this generalises across sessions, not across rooms. Three properties of the files have to be handled first, none of them a leakage risk but each capable of dominating a result: 2024-04-30 pairs a ZM-1 3OA render with a Spcmic 5OA render, so the orders differ; the 2024-08-15 Spcmic renders are 96 kHz against 48 kHz for the ZM-1 and SR-VRMIC; and the renders of a piece are not time-aligned (see [The leakage rule](#the-leakage-rule)).

**Not possible.** The corpus cannot support unit-to-unit variation (one physical unit per model), unseen-performer evaluation for piano (two pianists recur, covering seven of the eight solo-piano sessions), or any order-independent evaluation beyond truncating 5OA to 3OA/1OA (only five 5OA files exist).

## Reproducing

```sh
export HOA_CORPUS_DIR="/path/to/deposit"
python3 pyscripts/build_dataset_card.py --scan corpus_scan.csv
```

`corpus_scan.csv` is a per-file scan (path, session, filename, bytes, sha256, frames, channels, duration_s) of the deposit; `SHA256SUMS.txt` is written from the same scan. The scan file itself is not distributed with the deposit; regenerating it means walking the deposit's WAV files and hashing them.
